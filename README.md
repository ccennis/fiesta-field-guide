# Fiesta Field Guide

A collection manager for Fiesta, Riviera and Harlequin dinnerware. Two jobs: track what
is owned with value tracked over time, and answer "what is this, is it rare, what is it
worth, do I already own one" while standing in a shop holding a piece.

Runs fully offline. No API keys, no external calls.

## Getting started

```bash
composer setup
composer dev
```

Then open the URL printed by `php artisan serve`. `composer setup` migrates and imports
the collection; there are no other steps.

## The core distinction

The catalog of what Fiesta *is* is separate from the holdings the owner *has*.

- **Line** - Fiesta, Riviera, Harlequin. Part of identity: a Harlequin teapot and a
  Fiesta teapot are different objects, and Harlequin Red is not Fiesta Red.
- **Color** - belongs to a line, carries a production year range. The same name recurs
  across eras, so identity is line plus name plus start year. That is what keeps
  `Cobalt 1936-1951` and `Cobalt 1986-` apart.
- **Product** - the physical form: dinner plate, carafe, T&J mug. Belongs to a line, and
  carries no production years because the source data does not record them. The columns are
  absent rather than present and null. Products are editable, so names can be corrected and
  duplicates merged without breaking what already points at them.
- **Variant** - a product and color pairing, generated by crossing the two axes *within a
  line*. 1,797 rows against 150 owned pieces, which is the point: most of the catalog
  is what is not owned, and that is what identification needs.
- **Holding** - one row per physical object. Quantities in the spreadsheet are expanded.

### Era is derived, never stored

Era is read off the color's start year through `Era::fromYear()`. Vintage is 1936-1973,
post-86 is 1986 onward. No color in the source data starts between those ranges. A
color with no years has no era, and says so.

### Rarity is three separate facts

Nullable rarity sits on colors, products and variants. Nothing combines them into a score.
The interface shows "Medium Green: no rarity data" next to "covered onion soup: no rarity
data" and lets the reader do the work. A rarity set directly on a variant overrides both.

Null renders as *no rarity data*, never as *common*.

### Value is observed, not asserted

A `value_observation` names a product and optionally a color. A null color means the
figure applies to that product in any color. The most specific match wins, then the most
recent.

This exists because the owner's data is product level: one `$15 dinner plate` figure applied
across dozens of colors. Keying strictly on variant would have turned a single rough
guess into 48 confident looking rows. Instead there are 5 blanket rows and 55 specific
ones, tagged `default_schedule` versus `owner_estimate` so they can be told apart.

Condition is recorded but **never multiplied into value**. A condition multiplier would be
invented reference data. Value and condition are shown side by side.

### The catalog does not pretend to be verified

Variants are generated, so most were never confirmed to exist. `existence` starts
`unconfirmed` and is promoted to `confirmed` only where the source data evidences it.
Owning a piece is evidence. The interface says **no known example** rather than dressing a
generated row up as a real listing.

## Importing

Two commands, so a bad catalog run does not cost the holdings run.

```bash
php artisan fiesta:import-catalog --fresh
php artisan fiesta:import-holdings
```

Both print a reconciliation report and write it to
`storage/app/private/reports/`. **Nothing in the source data is silently resolved.** The
report covers cross-tab disagreements, quantity and value ambiguities, product names that
may describe one object, and every assumption the importer had to make.

The seed data in `database/seed-data/` is a real, uncleaned collection export. It is not
cleaned at source and should not be.

## API

All responses use `{ success, message, data, errors }`.

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/lines` | Lines |
| GET | `/api/products` | Product picker, `?line_id=` |
| GET | `/api/colors` | Color picker, `?line_id=` `?product_id=` `?era=` |
| GET | `/api/decorations` | Decal and novelty treatments |
| GET | `/api/variants` | `?owned=1\|0` `?line_id=` `?era=` `?product_id=` `?color_id=` |
| GET | `/api/variants/{id}` | The identification answer |
| GET | `/api/collection/summary` | Headline totals |
| POST | `/api/products` | Add a product |
| PATCH | `/api/products/{id}` | Rename a product |
| POST | `/api/products/{id}/merge` | Fold one product into another |
| DELETE | `/api/products/{id}` | Remove an unused product |
| PATCH | `/api/colors/{id}` | Edit hex |
| POST | `/api/holdings` | Record a piece |
| PATCH | `/api/holdings/{id}` | Condition and condition notes |

`/api/variants` backs both the collection view and the want list. They are the same query
with `owned` flipped. Unfiltered, "missing" is 1,647 rows, which is why the line, era and
product filters are not optional in practice.

The product write endpoints exist because product names arrive from a spreadsheet and
carry its typos. Correcting them in the interface has to be possible without detaching the
holdings that point at them.

## Known gaps

- **The want list is unbuilt.** Roughly 40 combinations the owner typed into the
  spreadsheet without owning them are indistinguishable from the 1,600 that are merely
  generated. The missing view cannot separate wanting something from never having seen it.
- **Eleven colors have no hex.** Heather, Ivory, Light Green, Peacock, Red, Red (Orange
  Red), Rose, Turquoise, Evergreen, Foundry and Linen render as dashed placeholders. The
  51 that do have values are community sourced and approximate, not measured from the
  pieces.
- **Value over time has a single date.** The spreadsheet carries none, so all 60
  observations are dated at import. The mechanism works and the data does not exercise it.
  No second date was invented to make it look better.
- **Product coverage is bounded by the collection.** The 42 products come from owned
  pieces, so anything never owned, including covered onion soup and the syrup, is not in
  the catalog and cannot be identified.
- **Six colors have no years,** and therefore no era, because the source embeds Fiesta's
  ranges on the Riviera and Harlequin rows and copying them across would be fabrication.
- **Two product pairs are still unresolved.** `Nappy 8.5"` and `Nappy Bowl` may be one
  object. `Canniser, Small` and `Cannister, Large` are two sizes carrying two different
  misspellings. The merge and rename tools exist; the rulings have not been made.
- **The starter's Post slice is still in the repo.** `Post`, `PostController`,
  `PostService` and `PostList.jsx` were the pattern reference and should have been deleted.
